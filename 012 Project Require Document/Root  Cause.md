# SMIS — Root Cause & Problem Statement

> [!warning] สถานะความน่าเชื่อถือของเอกสารนี้ ข้อมูลทั้งหมดสังเคราะห์จาก [[Master_PRD]] + persona จำลอง (**ยังไม่ได้สัมภาษณ์พยาบาลจริง**) ตัวเลขทุกตัวที่มีเครื่องหมาย ⚠️ คือ **สมมติฐานที่ต้องยืนยันด้วยข้อมูลจริง**

# ส่วนที่ 1 — Root Cause

## 1.1 อาการ / ผลลัพธ์ที่เห็นชัด (Symptoms)

|#|อาการที่สังเกตได้|ใครเจอ|
|---|---|---|
|S1|งานเปลี่ยน IV แทรกกลางคัน ต้องหยุดงานที่ทำอยู่ (เตรียมยา / ทำแผล)|พยาบาลประจำการ|
|S2|ญาติผู้ป่วยเป็นคนแจ้งก่อนพยาบาล|พยาบาลประจำการ|
|S3|เดินซ้ำเส้นทางเดิมทีละเตียง แทนที่จะรวบไปทีเดียว|พยาบาลประจำการ|
|S4|เวรที่งานหนัก รอบตรวจหลุด → IV หมดค้าง|พยาบาลประจำการ|
|S5|ญาติบ่น "เรียกแล้วไม่มา"|พยาบาล + หัวหน้าหอ|
|S6|ไม่มีข้อมูลเชิงตัวเลขเรื่องภาระงานของทีมเลย|หัวหน้าหอ|

## 1.2 5 Whys

```text
S1: งานเปลี่ยน IV กลายเป็นงานแทรกตลอดเวร
 │
 ├─ Why 1 → ทำไมถึงถูกแทรก?
 │   พยาบาลรู้ว่า IV จะหมด ก็ต่อเมื่อ "มันหมดไปแล้ว" และมีคนมาเรียก
 │
 ├─ Why 2 → ทำไมรู้ช้า?
 │   การประเมินทำได้แค่ตอนเดินผ่านเตียง = เป็น snapshot ไม่ใช่แนวโน้ม
 │
 ├─ Why 3 → ทำไมได้แค่ snapshot?
 │   ไม่มีใครวัด "อัตราการไหล" ต่อเนื่อง มีแต่ดูระดับน้ำด้วยตา
 │   ซึ่งบอกได้แค่ "เหลือเท่าไหร่" แต่ไม่บอก "อีกนานแค่ไหน"
 │
 ├─ Why 4 → ทำไมไม่รู้ "อีกนานแค่ไหน"?
 │   ไม่มี "มิติเวลา" อยู่ในระบบเลย ข้อมูลไม่ถูกบันทึกต่อเนื่อง
 │   จึงคำนวณล่วงหน้าไม่ได้
 │
 └─ Why 5 → ทำไมถึงยังเป็นแบบนี้?
     Workflow ทั้งระบบถูกออกแบบให้ "ตอบสนองหลังเกิดเหตุ" (reactive)
     ไม่ใช่ "วางแผนล่วงหน้า" (proactive)
     — และไม่มีใครมีข้อมูลมากพอที่จะเปลี่ยนมันได้
```

---

## 1.3 🎯 Root Cause (หลัก)

> [!important] Root Cause **หอผู้ป่วยไม่มี "มิติเวลา" ของสารน้ำ** รู้ได้แค่ว่า _ตอนนี้เหลือเท่าไหร่_ แต่ไม่รู้ว่า _อีกนานแค่ไหนจะหมด_ ทำให้งานเปลี่ยน IV เป็นงานที่ **วางแผนล่วงหน้าไม่ได้** และถูกบังคับให้เป็นงานแทรกเสมอ

**นัยต่อโปรดักต์:** ฟีเจอร์แกนคือ **Estimated Time to Empty (ETE)** และ **Priority Queue** — ไม่ใช่ Dashboard แสดง % สารน้ำ

---

## 1.4 Root Cause รอง (ฝั่งหัวหน้าหอ — คนละปัญหา แก้ด้วยฟีเจอร์คนละตัว)

> [!important] Root Cause รอง **ภาระงานพยาบาลไม่เคยถูกวัด** หัวหน้าหอจึงบริหารกำลังคนด้วยความรู้สึก และปกป้อง/ขออัตรากำลังให้ทีมด้วยหลักฐานไม่ได้

**นัยต่อโปรดักต์:** คุณค่าสำหรับหัวหน้าหอ = **Analytics / รายงานย้อนหลัง** ไม่ใช่ Real-time Dashboard

# ส่วนที่ 2 — Problem Statement

> [!note] ทำไมต้องแยก 2 ชุด Persona สองกลุ่มมีปัญหา "คนละเรื่อง" — พยาบาลคือ **ผู้ใช้** (ปัญหาระดับงานประจำวัน) หัวหน้าหอคือ **ผู้เสนอซื้อ** (ปัญหาระดับการบริหาร) ถ้ารวมเป็นอันเดียวจะได้โปรดักต์ที่ไม่ตอบใครเลย

---

## 📌 ชุด A — พยาบาลประจำการ (Primary User)

### ใคร

พยาบาลประจำการในหอผู้ป่วยสามัญ ที่ดูแลผู้ป่วยให้สารน้ำ **8–16 เตียงพร้อมกัน** ในหนึ่งเวร

### มีปัญหา

**ไม่รู้ล่วงหน้าว่าสารน้ำของแต่ละเตียงจะหมดเมื่อไหร่** รู้ได้แค่ "ตอนนี้เหลือเท่าไหร่" จากการเดินผ่านและมองด้วยตา จึงวางแผนรอบการเปลี่ยนถุงล่วงหน้าไม่ได้

### ส่งผลให้

- งานเปลี่ยน IV กลายเป็น **งานแทรก** ที่ถูกกระตุ้นจากญาติหรือกริ่ง ต้องหยุดงานที่ทำอยู่กลางคัน (เตรียมยา / ทำแผล) → เป็นจุดเสี่ยงความผิดพลาด
- **เดินซ้ำเส้นทางเดิม** ทีละเตียง แทนที่จะรวบไปเปลี่ยนทีเดียวหลายเตียง
- ในเวรที่งานหนัก **รอบตรวจหลุด** และเกิดกรณีสารน้ำหมดค้างไว้
- ญาติผู้ป่วยรับรู้ว่า "เรียกแล้วไม่มา" → กระทบความพึงพอใจและภาพลักษณ์หอ

### เกิดขึ้นเมื่อ

- เวรที่อัตราส่วนพยาบาลต่อเตียงสูงที่สุด (**เวรบ่าย / เวรดึก**)
- **ช่วงส่งเวร** (ข้อมูลอยู่ในความจำ ส่งต่อไม่ครบ)
- ช่วงที่พยาบาลติดงานที่ **หยุดกลางคันไม่ได้**

### ความถี่

|ตัวชี้วัด|ค่าประมาณ|สถานะ|
|---|---|---|
|งานเปลี่ยน IV แบบแทรกนอกรอบ|~4–6 ครั้ง **ต่อเวร**|⚠️ สมมติฐาน|
|IV หมดค้างโดยไม่มีใครรู้|~2–3 ครั้ง **ต่อสัปดาห์ ต่อหอ**|⚠️ สมมติฐาน|
|ญาติเป็นคนแจ้งก่อน|~50–70% **ของเคสทั้งหมด**|⚠️ สมมติฐาน|

---

## 📌 ชุด B — หัวหน้าหอผู้ป่วย (Buyer / Champion)

### ใคร

หัวหน้าหอผู้ป่วย ที่รับผิดชอบพยาบาล **12–18 คน** และ **30+ เตียง**

### มีปัญหา

**ไม่มีข้อมูลเชิงปริมาณเรื่องภาระงานและเวลาตอบสนองของทีมเลย** — ข้อมูลที่มีคือ "ความรู้สึกของน้องตอนส่งเวร"

### ส่งผลให้

- **จัดเวรด้วยความรู้สึก** ไม่ใช่ข้อมูลภาระงานจริง
- **ขออัตรากำลังเพิ่มไม่สำเร็จ** เพราะพูดได้แค่ "น้องเหนื่อยมาก" ซึ่งทุกหอพูดเหมือนกัน
- **รู้ว่ามีปัญหาก็ต่อเมื่อเกิด incident แล้ว** (เพราะถ้าไม่ถึงขั้นเขียนใบ incident ก็ไม่มีที่ไหนบันทึก)

### เกิดขึ้นเมื่อ

- ทุกรอบการจัดเวร
- ทุกครั้งที่ต้องเสนอของบประมาณ หรือชี้แจงเหตุการณ์ต่อฝ่ายการพยาบาล

### ความถี่

|ตัวชี้วัด|ค่าประมาณ|สถานะ|
|---|---|---|
|รอบจัดเวร|1 ครั้ง **ต่อเดือน**|ยืนยันแล้วจาก PRD/ทั่วไป|
|รายงานภาระงาน|1 ครั้ง **ต่อเดือน** (ทำจากความจำ)|⚠️ สมมติฐาน|

# ภาคผนวก — สมมติฐานเดิมใน PRD ที่ควรทบทวน

|PRD เดิมเชื่อว่า|สิ่งที่ Persona ชี้|นัยต่อโปรดักต์|
|---|---|---|
|ลดเวลาเดินตรวจ 50%|พยาบาลเดิน "รอบรวม" อยู่แล้ว IV เป็นแค่ 1 ใน 10 อย่างที่ดู|เปลี่ยน positioning เป็น **"ลดงานแทรก"** ไม่ใช่ลดเวลาเดิน|
|ไม่มีใครรู้ว่า IV ใกล้หมด|**ญาติเฝ้าไข้คือเซนเซอร์ตัวจริง** ที่มีอยู่แล้วและฟรี|คู่แข่งจริงไม่ใช่ "ไม่มีอะไรเลย"|
|Alert เยอะ = ดี|เกิน 3–4 ครั้ง/วันแบบไม่จำเป็น = เลิกใช้ใน 1 สัปดาห์|**False alert rate สำคัญกว่า accuracy**|
|หัวหน้าหอต้องการ real-time overview|หัวหน้าหอไม่อยู่หน้าจอ ต้องการรายงานย้อนหลัง|Analytics > Dashboard สำหรับ role นี้|
|ROI = ประหยัดค่าแรงพยาบาล|รพ. ไม่ได้ลดคนตามชั่วโมงที่ประหยัดได้|ROI ต้องเปลี่ยนเป็น **risk / satisfaction / staffing evidence**|
|ผู้ใช้คือคนซื้อ|คนเซ็นคือ ผอ. + คณะกรรมการเครื่องมือแพทย์ ที่ถาม **อย.** เป็นข้อแรก|Regulatory เป็น **gate** ไม่ใช่ risk ท้ายเอกสาร|
